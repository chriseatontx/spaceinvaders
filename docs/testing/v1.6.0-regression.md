# v1.6.0 Manual Regression Checklist

This checklist freezes the behavior of the current single-file `index.html` (version
`1.6.0`, line 83) before modularization. Every check below was written from the
current source, and the recorded result reflects what was actually executed in a
browser on 2026-10-18. Do not mark a check `PASS` without running it.

Line references are to `index.html` as it exists at v1.6.0.

## Setup

Run methods are only the ones documented in `README.md`:

1. Open `index.html` directly in a browser (`open` / `xdg-open`).
2. Serve the folder statically: `python -m http.server 8000` from the repository
   root, then open `http://localhost:8000/index.html`.

The recorded run below used method 2 (`python -m http.server 8000`), because the
recording harness cannot open `file://` URLs. Gameplay behavior is identical under
either method; only the harness limitation differs.

### Clean profile

Before the first check, in a fresh browser profile (or after clearing site data):

1. Confirm `localStorage` is empty (DevTools → Application → Local Storage).
2. Load the page. Expected first paint: title state, `CREDIT 00`, Score Credits
   `000000`, status `INSERT A QUARTER TO START`, Fire Control card hidden.

The recorded run started from an empty `localStorage` (`{}`).

### Harness note (how the recorded results were produced)

The checks were executed through a browser automation harness. Where a real input
device could not be used, the method is stated per check:

- **Real clicks**: the ADD QUARTER and INSTALL buttons were clicked as real
  accessibility-tree clicks.
- **Synthetic key events**: `KeyboardEvent` objects dispatched on `window`
  (`keydown` only, no matching `keyup`, so the game's frame loop sees the held key
  the same way a real key hold does). Used for Enter, arrows, `a`/`d`, and `m`.
- **Synthetic touch**: `PointerEvent` objects dispatched on the canvas with
  `pointerType: "touch"` and coordinates from the canvas rect. This exercises the
  page's real touch handlers, but it is not real touch hardware.
- **Input-only bots**: a `requestAnimationFrame` loop added by the harness that
  only sets `game.input.left/right` flags (and calls `game.addQuarter()` plus a
  synthetic Enter on game over). No game logic, state, or config was written by the
  harness; gameplay code was never modified.

## Known rough edges (found, not fixed)

- **R1 — Floor limit unreachable.** `GAME_OVER_FLOOR_MARGIN = 8` (line 101)
  feeds `dangerLine = Math.min(p.y, H − 8)` (line 578), but `p.y` is fixed 556,
  so the ship-line contact check (line 582) always wins. The 8 px floor band is
  dead in practice (check 17).
- **R2 — Constructor state churn.** The constructor runs `reset()` (which sets
  `state = "playing"`) and then sets `state = "title"` twice. Harmless today but
  confusing.
- **R3 — `input.touchTarget` survives `reset()`.** `reset()` does not clear
  `touchTarget`; only the constructor (line 719) nulls it. A stale target can
  steer the ship at the start of a new run.
- **R4 — Stale Enter can auto-restart.** If `input.enter` is still set when a run
  ends, the next frame consumes it and starts a new run, spending a quarter
  without a deliberate press.
- **R5 — `endTouch` clears `input.enter`.** `pointerup`/`pointercancel` clear
  both `touchTarget` and `enter` (lines 695–744), so a tap-to-start can be lost
  if `pointerup` arrives before the next frame.
- **R6 — Enter double-fires.** A keyboard Enter activates the focused cabinet
  `<button>` (ADD QUARTER / INSTALL) and simultaneously feeds game input, so one
  press can both accept a quarter and start a run.
- **R7 — Harness tap vs. button focus.** The automation harness's quick Enter tap
  at the title keyboard-activated the focused ADD QUARTER button and the frame
  loop missed the Enter (keyup cleared `input.enter` before the next frame).
  Consequence of R5/R6; recorded checks used keydown-only dispatch.
- **R8 — Readout wraps.** `cabinetPlays` is uncapped and the CREDIT readout is
  `("0" + n).slice(-2)` (line 366), so it wraps at 100 (`CREDIT 00`). Score
  Credits readout is `("000000" + n).slice(-6)` (line 367), wrapping at 1,000,000.
- **R9 — Mute not persisted.** `muted` is a module global, not saved; reload
  resets it to false (check 30).
- **R10 — UFO one-way.** The UFO always travels left→right (`dir: 1`, line 506);
  its drone also does not resume on unmute until the next update tick.
- **R11 — Fragile DOM coupling.** `syncCabinetUi` writes
  `cabinetPlaysNode.firstChild.nodeValue` (line 366); any markup change to the
  credit readout breaks the UI sync.
- **R12 — Hi-score key outside config.** `si-hiscore` is hardcoded (line 256)
  while the other keys live in `CABINET_CONFIG.storage` (lines 85–91).
- **R13 — No reduced-motion handling.** No `prefers-reduced-motion` rule exists
  in the stylesheet.

## Deterministic seams needed for automated tests

Current code has no injectable randomness or clock; these are the seams a test
harness would need:

- **UFO timer** — `ufoTimer = 15 + Math.random() * 10` (lines 307, 507).
- **UFO point band** — `UFO_POINTS[Math.floor(Math.random() * UFO_POINTS.length)]`
  (line 506).
- **Enemy shooter selection** — random pick from the alive list (line 522).
- **Enemy fire rate** — `Math.max(0.25, 0.9 - wave * 0.08) * (0.5 + Math.random())`
  (line 526).
- **Frame time** — the clock comes from `performance.now()` inside a
  `requestAnimationFrame` loop, clamped by `dt = Math.min(0.05, ...)`; it is not
  injectable and there is no fixed timestep, so simulation speed currently varies
  with display refresh.
- **No seedable RNG** — all four `Math.random()` uses above would need a shared,
  seedable source before scripted runs can be replayed byte-for-byte.
